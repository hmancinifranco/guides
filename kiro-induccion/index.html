📖 Glosario de Términos

Referencia rápida de todos los conceptos que usaremos en la sesión.

Kiro

IDE agéntico con IA: describes en lenguaje natural lo que necesitas y genera código funcional. Disponible como app de escritorio (IDE), línea de comandos (CLI) y navegador (Web).

Vibe Coding

Modo conversacional para implementación rápida. Describes lo que quieres en un prompt y Kiro genera el código. Ideal para tareas puntuales y prototipado veloz.

Spec-Driven Development

Enfoque estructurado para features complejas. Kiro genera Requisitos → Diseño → Tareas antes de escribir código. Da control total, trazabilidad y documentación automática.

Steering

Archivos markdown en .kiro/steering/ que dan a Kiro conocimiento persistente del proyecto: convenciones, stack tecnológico, estructura. Se cargan automáticamente en cada sesión.

MCP (Model Context Protocol)

Estándar abierto que conecta a Kiro con herramientas externas, APIs y fuentes de datos en tiempo real. Piensa en él como un "adaptador universal" para que la IA acceda a información actualizada.

Powers

Paquetes que combinan MCP + experiencia + workflows. Se activan automáticamente por contexto. Instalas un Power y Kiro gana expertise instantáneo en esa tecnología.

Subagents

Agentes especializados que Kiro delega para ejecutar tareas en paralelo. Cada uno tiene su propio contexto y retorna solo el resultado. Requieren modo Autopilot.

Agent Hooks

Disparadores automáticos tipo "si esto, entonces aquello". Ejecutan acciones ante eventos: guardar archivos, completar tareas, iniciar sesiones. Automatizan guardrails.

Agent Skills

Formato abierto y portable de conocimiento especializado. Se cargan bajo demanda (solo cuando son relevantes) a diferencia del Steering que está siempre activo.

Custom Agents

Configuraciones JSON reutilizables que definen un agente: su prompt, herramientas, permisos y recursos. Se guardan en .kiro/agents/ y se comparten con el equipo.

AI-DLC Discovery

Herramienta de discovery guiado para PMs y tech leads. Reemplaza la hoja en blanco con una entrevista estructurada que produce un Vision Document y un Technical Environment Document.

EARS (Easy Approach to Requirements Syntax)

Formato para escribir requisitos no ambiguos: WHEN <evento> THE SYSTEM SHALL <acción>. Asegura que cada requisito sea verificable y testeable.

Autopilot vs Supervised

Autopilot: Kiro aplica cambios de forma autónoma (necesario para subagents). Supervised: muestra los cambios para que los apruebes paso a paso.

🔐 ¿Cómo funciona por detrás?

Kiro se integra directamente con Microsoft Entra ID como Identity Provider:

  • Scopes solicitados: codewhisperer:completions y codewhisperer:conversations
  • Redirect URIs: configuradas por el admin en la app registration de Entra
  • SCIM provisioning: sincronización automática de usuarios y grupos desde Entra
  • Dominio verificado: el admin registró el dominio corporativo para habilitar SSO directo

🗂️ Dónde vive todo: la carpeta .kiro

Todas las funcionalidades core de Kiro (steering, skills, hooks, agents, specs, MCP) se almacenan como archivos de texto plano dentro de una carpeta oculta llamada .kiro. Esto significa que podés inspeccionarlos, editarlos manualmente y versionarlos en Git.

Existen dos niveles de configuración:

NivelUbicaciónAplica a
Proyecto (workspace)<raíz-del-repo>/.kiro/Solo este proyecto. Se commitea al repo → todo el equipo lo comparte.
Global (usuario)~/.kiro/Todos tus proyectos. Convenciones personales o del equipo vía MDM.

Regla de precedencia: si existe la misma configuración en ambos niveles, el workspace gana sobre el global. Steering, Skills y Hooks se mergean (se cargan ambos); MCP y Agents con el mismo nombre → el del workspace tiene prioridad.

📁 Estructura de subcarpetas dentro de .kiro/
# Nivel Proyecto (workspace) — raíz del repo
.kiro/
├── steering/          → Conocimiento persistente del proyecto (product.md, tech.md, structure.md)
├── skills/            → Paquetes de instrucciones bajo demanda (SKILL.md por carpeta)
├── hooks/             → Disparadores automáticos (archivos .json)
├── agents/            → Custom Agents del proyecto (.json o .md)
├── specs/             → Feature Specs y Bugfix Specs (requirements.md, design.md, tasks.md)
└── settings/
    └── mcp.json       → Servidores MCP configurados para este proyecto

# Nivel Global (usuario) — tu home directory
~/.kiro/
├── steering/          → Convenciones que aplican a TODOS tus proyectos
├── skills/            → Skills personales disponibles en cualquier workspace
├── hooks/             → Hooks que corren siempre, en todo proyecto
├── agents/            → Agentes disponibles globalmente
├── powers/            → Powers instalados (se activan por contexto)
└── settings/
    └── mcp.json       → Servidores MCP disponibles en todos los proyectos
💡 Tips prácticos
  • Commitear .kiro/ al repo — así todo el equipo comparte steering, hooks, agents y skills del proyecto.
  • Los Specs solo existen a nivel proyecto — no tiene sentido tenerlos globales.
  • Los Powers solo se instalan a nivel global — se activan dinámicamente según el contexto de trabajo.
  • Variable KIRO_HOME — permite mover ~/.kiro a otra ubicación (útil para múltiples perfiles en la misma máquina).
  • Kiro Web y Mobile solo leen la config de proyecto (la que está commiteada). No tienen acceso al ~/.kiro/ local.

# Project Structure

3. Configurar MCP mínimos

El ecosistema de MCP Servers para AWS tiene dos opciones principales:

AWS MCP (Toolkit) — Remoto, managed por AWS (GA)

Servidor remoto que combina acceso a APIs de AWS, documentación, Agent SOPs y CloudTrail logging. Requiere autenticación IAM (credenciales AWS configuradas). Ideal para equipos tech que ya tienen acceso programático a AWS. 📖 Blog de anuncio GA

AWS Documentation MCP Server — Local, sin autenticación ✅

Servidor local que da acceso a la documentación oficial de AWS en tiempo real. No requiere credenciales AWS, solo uvx. Ideal para empezar rápido y para el equipo de negocio.

Para esta inducción usamos el AWS Documentation MCP Server (sin fricción de credenciales).

Opción A — Instalar con un click:

1
Ir a awslabs.github.io/mcp/servers/aws-documentation-mcp-server
2
Click en el botón "Add to Kiro" → se configura automáticamente

Opción B — Configuración manual (crear .kiro/settings/mcp.json):

{
  "mcpServers": {
    "awslabs.aws-documentation-mcp-server": {
      "command": "uvx",
      "args": ["awslabs.aws-documentation-mcp-server@latest"],
      "env": {
        "FASTMCP_LOG_LEVEL": "ERROR",
        "AWS_DOCUMENTATION_PARTITION": "aws"
      },
      "disabled": false,
      "autoApprove": []
    }
  }
}

Prerequisito: instalar uv (incluye uvx):

curl -LsSf https://astral.sh/uv/install.sh | sh

🤖 Headless Mode — Kiro CLI sin intervención humana Tech

El modo headless permite ejecutar Kiro CLI de forma programática, sin browser ni interacción manual. Ideal para CI/CD, cron jobs, scripts de automatización y cualquier entorno donde no hay un humano sentado frente a la terminal.

¿Cómo funciona?

1
Generar un API Key — desde app.kiro.dev → Account Settings
2
Setear la variable de entorno — export KIRO_API_KEY=tu-api-key
3
Ejecutar con --no-interactive — Kiro imprime la respuesta a stdout y termina

Eso es todo. Con KIRO_API_KEY seteada, Kiro CLI salta el login por browser automáticamente.

Ejemplo: Code Review automático en CI

# En tu pipeline (GitHub Actions, GitLab CI, etc.)
- name: Install Kiro CLI
  run: curl -fsSL https://cli.kiro.dev/install | bash

- name: Run code review
  env:
    KIRO_API_KEY: ${{ secrets.KIRO_API_KEY }}
  run: |
    kiro-cli chat --no-interactive \
      --agent code-reviewer \
      "Review all changes for security issues, bugs, and best practices"

Casos de uso

CasoDescripción
Code review automatizadoRevisar cada push por seguridad, bugs y best practices
Generación de documentaciónEscanear código y actualizar docs en cada merge a main
Auditoría de dependenciasDetectar paquetes outdated o vulnerables
Resúmenes de PRGenerar descripciones legibles de los cambios
Asistencia en migracionesIdentificar patrones que necesitan actualizarse
💡 El patrón es siempre el mismo

Un API key + un custom agent + un one-liner en tu CI config. Definí el agente en .kiro/agents/, commitealo al repo, y dejalo correr en cada push.

🔍 AI-DLC Discovery Ambos

Herramienta de product discovery guiado que reemplaza la hoja en blanco con una entrevista estructurada por roles (negocio y técnico).

¿Qué es?

AI-DLC Discovery es una entrevista guiada que produce los documentos que el equipo de tecnología necesita para empezar a implementar. No genera código — genera claridad.

¿Quién lo usa?

RolQué haceOutput
Product Manager / AnalistaResponde preguntas de negocioVision Document
Tech Lead / ArquitectoDefine stack y restriccionesTechnical Environment
AmbosRevisión cruzadaOpen Questions

¿Cómo se usa? (con Kiro CLI o IDE)

1
Instalar automáticamente — pegar este prompt en Kiro (CLI o IDE) y dejar que haga todo: 
Set up aidlc-discovery v2 in this project.
Do every step yourself and report back when done:

1. Detect which platform you are running in:
   Kiro, Claude Code, or Amazon Quick desktop.

2. Download the matching asset from the v2.0.1 release
   (replace <platform> with kiro | claude | quick):
   https://github.com/aws-samples/
   sample-aidlc-discovery/releases/download/
   v2.0.1/aidlc-discovery-<platform>-v2.0.1.zip

3. Unzip and install to the platform's location:
   - kiro   -> merge the bundle into ./.kiro/
   - claude -> merge the bundle into ./.claude/
   - quick  -> import the aidlc-discovery/ skill
               folder through the Quick desktop UI
               (Agents & skills -> Skills tab ->
               + Create -> Import from file ->
               select SKILL.md).

4. Confirm the install path and the invocation phrase
   (Kiro / Quick: "start aidlc-discovery";
    Claude Code: "/aidlc-discovery").

5. Configura el archivo:
   aidlc-discovery-rules/aidlc-discovery-rule-details/
   common/language-handling.md
   para que los user-facing documents e interacciones
   sean en Español.

El agente detecta la plataforma, descarga el bundle correcto, lo instala y configura el idioma. 📖 Instrucciones completas

2
Iniciar sesión de discovery — escribir start aidlc-discovery en el chat (funciona igual en Kiro IDE y Kiro CLI). Podés incluir la idea en el mismo mensaje: 
start aidlc-discovery. Mi Proyecto: Una plataforma interna que permite a los
empleados enviar ideas innovadoras para evaluación transparente...

Tip: podés pre-cargar contexto antes de invocar: "Leé ./docs/requisitos.md primero, luego start aidlc-discovery". 📖 Guía completa de uso

3
Seleccionar rol (Business o Technical) y modo (conversational o batch)
4
Responder las preguntas sección por sección
5
Obtener los documentos en Product-Definition/
💡 Tip: alimentá el discovery con fuentes existentes

No necesitás responder todo de memoria. Podés usar documentación previa o conectores MCP a sistemas como Jira, Confluence, SharePoint o cualquier otro compatible con MCP para que el agente proponga respuestas a partir de esa información. Ejemplos:

  • "Leé ./docs/requisitos-negocio.pdf primero, luego start aidlc-discovery"
  • "Usá el MCP de Confluence para traer la página 'Arquitectura del Producto', luego start aidlc-discovery"
  • "Consultá los tickets del epic PROJ-123 en Jira, luego start aidlc-discovery"

El agente pre-llena las respuestas con la información encontrada — vos solo revisás y aprobás en cada gate.

¿Qué produce?

Product-Definition/
├── vision-document.md          → qué construir y por qué
├── technical-environment.md    → stack, herramientas y restricciones
├── open-questions.md           → ambigüedades pre-declaradas
├── state/                      → estado para retomar sesión
├── audit/                      → log de auditoría por rol
└── interview/                  → historial de respuestas

El puente con Tecnología

Discovery → Specs → Código

Los documentos que produce Discovery alimentan directamente las Feature Specs que usa el equipo tech. El Vision Document se convierte en requisitos EARS, y el Technical Environment guía las decisiones de diseño.

📐 Spec-Driven Development Tech

Enfoque estructurado para construir features complejas con control total y trazabilidad.

Tipos de Spec

TipoCuándo usarlaPunto de partida
Feature Spec (Requirements-first)Sabes QUÉ construirVision Document de Discovery
Feature Spec (Design-first)Sabes CÓMO construirloArquitectura predefinida
Bugfix SpecSabes QUÉ está rotoBug report
💡 Tip: conectá Discovery con Specs

Los documentos que genera AI-DLC Discovery (Product-Definition/vision-document.md, technical-environment.md) son el input ideal para iniciar una Feature Spec. Al crear la spec, referenciá esos archivos y Kiro los usa como base para generar requisitos EARS, diseño técnico y tareas — toda la investigación previa del equipo de negocio se traduce automáticamente en un plan de implementación estructurado.

Flujo de una Feature Spec

1
Requisitos (EARS) — Criterios de aceptación verificables
WHEN usuario envía formulario THE SYSTEM SHALL validar campos obligatorios
2
Diseño — Arquitectura, modelos de datos, APIs, puntos de integración
3
Tareas — Discretas, ordenadas por dependencia, ejecutables por subagents
4
Ejecución — Kiro implementa con subagents en paralelo (modo Autopilot)

Subagents — Trabajo en paralelo

¿Qué son?

Agentes especializados que Kiro despacha para ejecutar tareas independientes en simultáneo. Cada uno tiene su propia ventana de contexto y retorna solo el resultado final.

SubagentPropósito
Context GathererExplora el proyecto e identifica archivos relevantes
General-PurposeManeja subtareas bien definidas de forma autónoma
Custom (tu equipo)Definidos en .kiro/agents/ — ej: security-agent, infra-agent

Vibe vs Spec — Regla rápida

¿Cuándo usar cada uno?

Vibe: si lo puedes describir en 1 frase → "creame un endpoint de health check"

Spec: si necesitas un párrafo o más → feature multi-archivo, sistema completo, cambio arquitectónico

Kiro tiene tres superficies. Usa la que mejor se adapte a tu rol y momento.

SuperficieIdeal paraPúblico sugerido

Comandos clave del CLI

# Iniciar chat interactivo
kiro-cli chat

# Ejecutar un prompt directo (one-shot)
kiro-cli chat "tu prompt aquí"

# Modo headless (CI/CD, scripts)
kiro-cli chat --no-interactive "prompt"

# Agregar contexto
/context add ./src/

# Ver herramientas MCP disponibles
/tools

# Ver servidores MCP
/mcp

# Usar un custom agent
/agent mi-agente
